# 🗺️ Когда что использовать — Дерево решений

---

## 🌳 Дерево решений

### Главный алгоритм выбора

```
ВОПРОС 1: Это разовая задача без повторений?
│
├─► ДА → Используй 💬 PROMPT
│         Пример: "Переведи это письмо", "Объясни ошибку"
│
└─► НЕТ → ВОПРОС 2 ↓

ВОПРОС 2: Нужен доступ к внешним данным/системам?
│
├─► НЕТ → ВОПРОС 3 ↓
│
└─► ДА → Добавь 🔌 MCP к решению → ВОПРОС 3 ↓

ВОПРОС 3: Нужно единообразное поведение AI для всей команды/продукта?
│
├─► ДА → Нужны 📋 INSTRUCTIONS
│         Плюс MCPs, если ответили ДА на вопрос 2
│         → ВОПРОС 4 ↓
│
└─► НЕТ → ВОПРОС 4 ↓

ВОПРОС 4: Задача специализирована и повторяется регулярно?
│
├─► ДА → Создай 🎯 SKILL
│         Пример: code-review каждый PR, HR-оценка каждого кандидата
│
└─► НЕТ → ВОПРОС 5 ↓

ВОПРОС 5: Задача требует нескольких шагов и принятия решений?
│
├─► ДА → ВОПРОС 6 ↓
│
└─► НЕТ → Достаточно Prompt + Instructions + MCP

ВОПРОС 6: Порядок шагов известен заранее? Нужна надёжность/аудит?
│
├─► ДА (порядок известен, нужна надёжность) → 🔄 WORKFLOW
│    Пример: обработка заявок, document pipeline, ETL
│
└─► НЕТ (нестандартная задача, нужна адаптивность) → 🤖 AGENT
     Пример: исследование, нестандартный анализ, DevOps
```

## 📋 Принцип KISS: Не усложняй без причины

### «Лестница усложнения» — добавляй слой только при необходимости

```
УРОВЕНЬ 0: Промпт
"Можешь это сделать простым промптом?" → Да? → Стоп.

УРОВЕНЬ 1: Добавляем Instructions
"Нужно делать это регулярно с одинаковым стилем?" → Да? → Добавь.

УРОВЕНЬ 2: Добавляем MCPs  
"Нужны реальные данные из внешних систем?" → Да? → Добавь.

УРОВЕНЬ 3: Добавляем Skills
"Эта логика повторяется много раз в разных контекстах?" → Да? → Добавь.

УРОВЕНЬ 4: Добавляем Agent
"Нужна автономность и адаптация?" → Да? → Добавь.

УРОВЕНЬ 5: Заворачиваем в Workflow
"Нужна надёжность, восстановление, аудит?" → Да? → Добавь.
```

### Правило:
> **Используй минимально достаточный уровень.** Каждый следующий уровень — это дополнительная сложность, стоимость и ответственность. Оправдывай переход необходимостью, а не желанием использовать «крутую технологию».

## 🔧 Как концепты комбинируются — Реальные стеки

### Стек 1: Простой корпоративный помощник
```yaml
Задача: Ассистент для HR-отдела

Компоненты:
  Instructions: "Ты HR-ассистент компании X. Отвечай по корпоративным политикам."
  MCPs:
    - hr-database (читает данные о сотрудниках)
    - sharepoint (документы политик)
  Skills:
    - leave-calculation (расчёт отпусков)
    - policy-lookup (поиск по политикам)

Без Agents и Workflows — задача не требует автономности
```

### Стек 2: Умный code-ревьюер в CI/CD
```yaml
Задача: Автоматический code-review каждого PR

Компоненты:
  Workflow:       
    trigger: PR opened
    steps:
      1. MCPs: [github-mcp] читает изменения PR
      2. Skills: [code-analysis] анализирует код
      3. Skills: [security-check] проверяет безопасность
      4. Instructions: [review-style] определяет тон комментариев
      5. MCPs: [github-mcp] публикует комментарии
      6. Если критичные проблемы → Block PR
      
Нет Agent — задача детерминированная и хорошо описана
```

### Стек 3: Исследовательский агент
```yaml
Задача: Исследование конкурентного ландшафта

Компоненты:
  Instructions: "Ты аналитик рынка. Объективен, ссылайся на источники."
  MCPs:
    - web-search (поиск актуальных данных)
    - file-write (сохранение отчёта)
  Skills:
    - competitive-analysis (шаблон анализа конкурентов)
    - report-generation (структура отчёта)
  Agent: ReAct agent (сам решает что и как исследовать)
  
Нет Workflow — порядок исследования нельзя предугадать заранее
```

### Стек 4: Enterprise AI-конвейер (полный стек)
```yaml
Задача: Обработка клиентских заявок на кредит

Workflow (детерминированная оболочка):
  Step 1: MCP → получить заявку из CRM
  Step 2: Skill → валидация данных
  Step 3: AI (Instructions) → классификация риска
  Step 4: MCP → запрос кредитной истории
  Step 5: Agent → комплексный анализ (нестандартные случаи)
  Step 6: Skill → генерация решения
  Step 7: Human approval (для сумм > 500K)
  Step 8: MCP → отправить решение в CRM + email клиенту
```

## 🚫 Антипаттерны — Типичные ошибки выбора

### Антипаттерн 1: «Агент на всё»
```
❌ Неправильно:
"Нам нужно обрабатывать 10,000 счетов в день → создадим агента!"

Проблемы:
  - Агент стоит в 10-15x дороже простого вызова LLM
  - Нет гарантии, что все 10K обработаны
  - Сложно мониторить прогресс
  - При сбое — где остановились?

✅ Правильно:
Workflow с 2-3 AI-шагами
```

### Антипаттерн 2: «Промпт вместо Instructions в продукте»
```
❌ Неправильно:
Каждый разработчик пишет свой системный промпт для общего бота

Проблемы:
  - Разное поведение у разных пользователей
  - Нет версионирования правил
  - Нет единой политики безопасности

✅ Правильно:
Централизованный файл Instructions + git
```

### Антипаттерн 3: «Мегонавык»
```
❌ Неправильно:
SKILL: "FullCycleDevAssistant" — анализирует, пишет код, 
        тестирует, документирует, деплоит, мониторит...

Проблемы:
  - Нарушение Single Responsibility
  - Сложно тестировать отдельные аспекты
  - При изменении одного аспекта — меняется всё

✅ Правильно:
  SKILL: code-analysis
  SKILL: test-generation
  SKILL: documentation
  SKILL: deployment-checklist
  (комбинируются агентом или workflow)
```

### Антипаттерн 4: «MCP без безопасности»
```
❌ Неправильно:
MCP-сервер с правами:
  - read_all_files
  - write_all_files  
  - delete_files
  - execute_commands
  - access_all_databases

Риск: AI + ошибка = катастрофа

✅ Правильно:
MCP-сервер с принципом least privilege:
  - read_files(path_pattern="/workspace/src/**")
  - write_files(path_pattern="/workspace/src/**")
  - NO delete, NO execute, NO DB write без review
```

### Антипаттерн 5: «Workflow без AI» (или наоборот)
```
❌ Workflow без AI там, где нужна гибкость:
if category == "technical": route_to_tech()
elif category == "billing": route_to_finance()
elif category == "general": route_to_support()
# А если категория "technical+billing"? 
# А если новая категория появится?

✅ AI-классификация в узле:
category = ai_classify(ticket)  # Гибко, обрабатывает edge cases
route_to(category)
```

## ✅ Чек-лист перед выбором инструмента

```
□ Задача разовая или повторяющаяся?
□ Нужен доступ к внешним системам/данным?
□ Задача выполняется для одного человека или многих?
□ Нужна гарантия результата (надёжность)?
□ Есть ли чёткий алгоритм или нужна адаптивность?
□ Каков бюджет на LLM-вызовы?
□ Нужен аудиторский след?
□ Есть ли время на построение инфраструктуры?
□ Насколько критичны ошибки?
□ Нужно ли масштабировать на тысячи запросов?
```

## 🗓️ Эволюционный подход: «Начни с малого»

```
ДЕНЬ 1:  Промпт (проверяешь идею)
ДЕНЬ 7:  + Instructions (стандартизируешь поведение)
МЕСЯЦ 1: + MCP (добавляешь данные)
МЕСЯЦ 2: + Skills (выделяешь повторяющиеся паттерны)
МЕСЯЦ 3: + Agent (добавляешь автономность для сложных случаев)
МЕСЯЦ 6: + Workflow (промышленная надёжность)
```

**Ключевой принцип:**
> Не строй Workflow на день 1, если не знаешь, работает ли идея вообще.  
> Не используй промпт в продакшене с тысячами пользователей без Instructions.  
> Двигайся итеративно.

## 🎤 Заметки для спикера

- **Дерево решений** — хороший интерактивный слайд: «Давайте вместе пройдём по дереву для вашей задачи»
- **KISS принцип** — важная ремарка: многие разработчики хотят сразу строить агентов. Объясни, почему это неправильно
- **«Эволюционный подход»** — очень практичная рекомендация. Большинство успешных AI-продуктов начинали с малого
- **Антипаттерны** — аудитория смеётся, узнавая свои ошибки. Это хорошо
- Предложи аудитории: «Есть ли у кого-то реальная задача? Давайте пройдём по дереву решений вместе»
- Время на этот слайд: **7 минут**
