# 🧭 Локальная демонстрация в VS Code / VS 2026

---

## Цель этого файла

Этот документ нужен для живой демонстрации цепочки:

Prompts → Instructions → Skills → MCP → Agent → Workflow

Он написан так, чтобы по нему можно было провести наглядный demo-сценарий локально, шаг за шагом.

---

## Короткий ответ на главный вопрос

Да, в целом вы правильно понимаете идею:

1. Сначала можно показать обычные prompts.
2. Потом из них выделить устойчивые правила и оформить instructions.
3. Затем объединить повторяющуюся логику в skills.
4. Потом подключить MCP, если у вас есть MCP-совместимый клиент и локальный или внешний MCP-сервер.
5. Затем создать агента, который использует instructions, skills и tools.
6. И уже после этого показать workflow, в который агент встроен как один из шагов.

Но важно уточнение:

- **Prompts, Instructions, Skills и Agent-артефакты** вы действительно можете подготовить локально в VS Code.
- **MCP** тоже можно показать локально, но только если у вас есть рабочий MCP-сервер и клиент/расширение, которые умеют с ним работать.
- **Workflow** локально тоже можно показать, но чаще всего как GitHub Actions, task runner, скрипт-оркестратор, diagram-first сценарий или внешний пайплайн.

---

## Что именно лучше показать в demo

### Сценарий demo-задачи
Используйте одну сквозную задачу, например:

"Подготовить ответ клиенту по статусу заказа и при необходимости эскалировать сложный кейс"

Это удобно, потому что на одной задаче можно показать все уровни зрелости.

---

## Шаг 1. Показать обычный Prompt

### Что нажимать в VS Code
1. Откройте окно чата Copilot.
2. Создайте новый чат.
3. Введите базовый запрос вручную.

### Что вводить
```text
Напиши ответ клиенту о задержке заказа на 2 дня.
```

### Что объяснять аудитории
- Это самый простой уровень.
- Он быстрый, но нестабильный.
- Один сотрудник напишет один prompt, другой сотрудник другой.

---

## Шаг 2. Получить из prompt'ов Instructions

### Что нажимать
1. В Explorer откройте корень проекта.
2. Если папки `.github` нет, создайте ее.
3. Внутри `.github` создайте файл `copilot-instructions.md`.

### Что добавить в файл
```markdown
# Инструкции для ассистента поддержки

- Всегда отвечай на русском языке.
- Тон: вежливый, деловой.
- Не придумывай факты о заказе.
- Если данных недостаточно, так и напиши.
- В конце добавляй блок "Следующий шаг".
```

### Что объяснять
- Теперь мы не просто задаем разовый запрос.
- Мы зафиксировали постоянные правила поведения.

---

## Шаг 3. Упаковать повторяемую логику в Skill

### Что нажимать
1. В Explorer откройте `.github`.
2. Создайте папку `skills`.
3. Внутри нее создайте папку `customer-reply`.
4. Внутри `customer-reply` создайте файл `SKILL.md`.

### Что вставить в `SKILL.md`
```markdown
---
name: customer-reply
description: 'Готовит ответ клиенту по статусу заказа. Use when: customer support, order delay, shipment status, reply to customer.'
---

# Customer Reply

## When to Use
- Нужно ответить клиенту по статусу заказа
- Нужно вежливо сообщить о задержке

## Procedure
1. Определи, хватает ли данных для ответа
2. Сформулируй краткое извинение
3. Сообщи статус и новую дату, если она известна
4. Добавь следующий шаг
```

### Что объяснять
- Prompt превратился в повторяемый модуль.
- Это уже не разовая импровизация, а переиспользуемая способность.

---

## Шаг 4. Добавить второй Skill

### Что нажимать
1. В `.github/skills` создайте папку `policy-check`.
2. Внутри создайте `SKILL.md`.

### Что вставить
```markdown
---
name: policy-check
description: 'Проверяет, не нарушает ли ответ корпоративную политику. Use when: compliance, support reply, policy validation.'
---

# Policy Check

## Procedure
1. Проверь, нет ли персональных данных
2. Проверь, нет ли вымышленных фактов
3. Убедись, что следующий шаг указан явно
```

### Что объяснять
- Один большой skill лучше разбивать на узкие навыки.
- Это полезно и для агента, и для workflow.

---

## Шаг 5. Подключить MCP

### Важное уточнение
Вот здесь начинается часть, которая **может быть показана локально, но зависит от окружения**.

### Что нужно для demo
1. MCP-совместимый клиент.
2. Настроенный MCP-сервер.
3. Источник данных: файл, API, mock CRM или GitHub.

### Самый безопасный demo-вариант
- read-only MCP к локальному JSON-файлу со статусами заказов;
- или read-only MCP к GitHub/файлам.

### Что объяснять
- Skill не дает доступ к данным.
- MCP не задает стиль и логику ответа.
- MCP отвечает за доступ к реальному контексту.

---

## Шаг 6. Создать агента

### Что нажимать
1. В `.github` создайте папку `agents`.
2. Внутри создайте файл `support-agent.agent.md`.

### Что вставить
```markdown
---
name: support-agent
description: 'Агент поддержки клиентов. Use for: support automation, order status, escalation, policy-aware replies.'
tools: []
---

# Support Agent

Ты обрабатываешь обращения клиентов по статусу заказов.

## Правила
- Сначала выясни, достаточно ли данных
- Если доступны инструменты, используй их для проверки фактов
- Для ответа используй skill customer-reply
- Перед финальным ответом используй skill policy-check
- Если данных недостаточно или кейс спорный, эскалируй человеку
```

### Что объяснять
- Агент координирует steps и решает, что делать дальше.
- Он использует instructions, skills и при наличии tools/MCP.

---

## Шаг 7. Подключить к Workflow

### Что показать
Здесь не обязательно сразу строить сложную инфраструктуру. Для demo достаточно показать один из форматов:

1. YAML workflow;
2. diagram-as-code;
3. простой Python-оркестратор;
4. GitHub Actions pipeline.

### Пример логики workflow
```text
1. Получить новое обращение
2. Проверить данные заказа через MCP
3. Передать задачу support-agent
4. Прогнать policy-check
5. Если confidence низкий -> эскалация человеку
6. Иначе отправка ответа
7. Запись результата в журнал
```

### Что объяснять
- Workflow задает каркас процесса.
- Агент становится одним из узлов, а не всей системой сразу.

---

## Поместится ли это в одну демонстрацию

Да, если показывать не все детали реализации, а **логику на одном сквозном кейсе**.

### Реалистичный тайминг
- Prompts: 2-3 минуты
- Instructions: 2 минуты
- Skills: 4-5 минут
- MCP: 3-5 минут
- Agent: 3-4 минуты
- Workflow: 3-4 минуты

Итого: примерно 18-23 минуты demo-части.

Для основной презентации это помещается, если:
- на слайдах держать только идею и 1 ключевой пример;
- технические детали раскрывать в этом файле, а не на основном слайде.

---

## Практическая рекомендация

Для live-demo не пытайтесь сразу показать production-grade MCP и production workflow.

Лучше показать:
1. один базовый prompt;
2. один файл instructions;
3. два небольших skill;
4. один безопасный read-only MCP;
5. одного агента;
6. один компактный workflow.

Так демонстрация будет понятной, правдоподобной и поместится по времени.
